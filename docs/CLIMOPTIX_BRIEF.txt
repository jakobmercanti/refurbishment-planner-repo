============================================================
1. PRODUCT VISION, ARCHITECTURE AND HARD BOUNDARIES
============================================================

Create "Climoptix" as a dedicated CFD MODE / WORKSPACE inside the SAME shared
application codebase used by FreeFloorplan3D and PlannerBuild. Do not duplicate or
fork the floorplan editor, 3D scene model, asset library, storage or user system.

The user should be able to:
  1. Draw or load an existing room/building using the common planner.
  2. Switch to "Climoptix / CFD" from a clear, discoverable entry point.
  3. Select ONE physically connected air domain for a CFD case, even when it spans
     more than one room or multiple floors through unobstructed openings.
  4. Place supply inlets, extract outlets, and optionally equipment and other
     relevant sources, using the existing 2D and 3D editing facilities.
  5. Treat furniture and people as actual physics-aware objects with simplified CFD
     geometry and configurable obstruction/thermal/contaminant properties.
  6. Configure boundary conditions, working fluid, physics, initial conditions,
     turbulence, time settings, solver controls, meshing and resource limits.
  7. Inspect an accurate 3D PREVIEW of the selected fluid domain and its boundary
     patches, validate it, and SAVE or EXPORT a reproducible CFD scenario.
  8. Later (once integrated) mesh, run, monitor and visualise OpenFOAM CFD; later
     still run our proprietary inlet/outlet position optimiser.

These are THREE DIFFERENT PRODUCT ENTRY POINTS but ONE shared editor and geometry
model. Brand/mode switching and feature flags must not create parallel application
copies. Floor planning is still available in Climoptix; HVAC engineers also need
plan views, furniture, 3D, measurements and exports. A future commercial packaging
system may decide which modules are unlocked: DO NOT implement pricing/paywalls now.

INITIAL ANALYSIS SCOPE:
- One connected fluid volume per CFD case. This can be a single room, two rooms
  joined by a PERMANENT unobstructed opening, or a double-height/stairwell-connected
  space, including across floors if floor openings truly connect air volumes.
- Do not require a whole-building CFD domain and do not make every adjacent room
  automatically join the calculation.
- Geometry first. OPENFOAM BACKEND LATER. Never display invented CFD results or
  claim to have performed actual meshing/flow simulation without a solver.

STRONG MODE SEPARATION:
- The geometry, drawing tools, units, save/load and assets remain shared.
- CFD-specific semantics, scenarios, vent definitions, boundary conditions, mesh
  recipes and simulations live in a distinct Climoptix module; their visibility is
  restricted to CFD mode unless the user opens a read-only engineering summary.
- A project can store MULTIPLE named CFD scenarios targeting different connected
  spaces without losing any building objects or duplicating the building geometry.

4. CRITICAL: SELECT A CFD DOMAIN BY CONTINUITY OF AIR VOLUME
============================================================

This is a NON-NEGOTIABLE rule of this product.

User selects a SEED ROOM / seed connected zone. The software constructs the
connected air domain by traversing only genuinely unobstructed, permanent air
connections. It must ALWAYS STOP at a DOOR or WINDOW, whether the door/window is
marked OPEN or CLOSED, partially open, sliding, internal, external, etc.

Doors and windows are HARD DOMAIN SELECTION BOUNDARIES. Their user-selected
open/closed state affects the corresponding BOUNDARY CONDITION if enabled, not
whether the neighbouring room becomes part of the selected simulation.

Pass-through examples:
- Two rooms joined by a permanent archway or wall opening WITHOUT a door or
  window object: same continuous air volume -> include both automatically.
- A double-height atrium or stairwell connected through a true slab opening:
  include the connected portion across floors, if properly bounded.
- An internal open-plan area with no separating wall: remains one continuous
  domain. Do not accidentally split it based only on visual room labels.

Stop examples:
- Two rooms linked by a DOOR object marked open -> STOP at the door plane.
- The same door marked closed -> STOP at the door plane.
- A WINDOW object marked open -> STOP at the window plane.
- The same window marked closed -> STOP at the window plane.
- A doorless doorway MUST have an explicit 'permanent opening / archway' semantic
  type to be traversable. Do not change a door to an archway merely because its
  door leaf is hidden.
- A closed wall, floor slab or ceiling -> STOP unless an explicit void/portal
  proves a continuous fluid connection.

Implementation approach:
A. Build an abstract TOPOLOGICAL CONNECTION GRAPH of air regions with semantic
   portals and blockers derived from actual building geometry:
     Room/air-region node -> adjacent region node + opening semantics.
   Or construct a robust geometric flood-fill over connected cells/surfaces if the
   existing engine already supports it. Do not use room-ID equality alone.
B. Traverse via BFS/DFS only if the connection is geometrically valid and its
   semantic type is 'open passage', 'archway', 'floor void' or a validated equivalent.
C. Doors/windows are traversal blockers regardless of state; they must still
   appear in the boundary patch list and the 3D cut-cap geometry.
D. Where the domain terminates at an open door/window, create a VIRTUAL CFD
   BOUNDARY SURFACE across its opening plane. The opening is not erroneously
   treated as a solid wall: the user may assign pressure/velocity/exchange BCs.
   It is just the boundary of THIS selected domain. A closed door/window may be
   solid/no-slip with thermal transfer according to its selected BC.
E. Show the selection visually and explicitly: coloured included rooms, non-
   included rooms ghosted, arrows indicating passable permanent openings, red/
   labelled 'domain stops here' markers at all doors and windows.
F. Preserve stable room and patch IDs and source-object provenance, including
   floor IDs. When the model changes, recompute connectivity and invalidate the
   derived domain / mesh recipe if needed; do not silently use stale geometry.
G. Only one connected domain per scenario. If user explicitly includes an
   unconnected region, explain the connectivity rule and offer a separate scenario
   rather than silently merging disconnected fluid volumes.
H. Handle ambiguous regions, duplicate openings, invalid polygons, intersecting
   floor voids, collapsed slabs, model gaps or room volume overlaps with a
   specific validation error. Do not 'heal' a blocked door into an open passage.
I. Distinguish a stair MODEL (furniture/obstacle) from a true floor OPENING; stairs
   themselves do not imply a fluid passage unless slab geometry allows it.
J. Consider variable footprint upper floors, stepped ceilings, roof-following
   sloped ceilings and independent internal suspended ceilings. CFD uses the
   INTERIOR air boundary, not the external roof silhouette.

Provide a domain-inspection report listing:
- Seed ID, participating room/zone IDs, involved floor IDs and opening IDs.
- Continuous-volume topology, eligible portals and blocked doors/windows.
- Air volume, domain bounds, open/closed boundary patches and surface areas
  (where these can be computed accurately).
- Boundary patch IDs, types, associated editable source objects and normals.
- Missing/unresolvable geometry or reasons connectivity cannot be established.

IMPORTANT EXAMPLE TESTS:
1. Room A -> permanent archway -> Room B: selecting A includes A+B.
2. Room A -> OPEN door -> Room B: selecting A includes ONLY A.
3. Same door CLOSED: still ONLY A.
4. Room A -> OPEN window -> outside or another region: STOP at window.
5. Room A -> stairwell slab void -> upper connected volume: both levels included.
6. Two disconnected upstairs regions: do not merge just because same building.
7. A window cut-out in a wall does not become an unconstrained fluid connection.
8. Deleting / moving a door or wall recomputes the correct selection and patches.

5. FLUID-DOMAIN GEOMETRY AND CFD PREPROCESSOR
============================================================

The CFD model must be derived from the EXISTING SOURCE BUILDING MODEL, but stored
as a versioned, reproducible SCENARIO SNAPSHOT (or references plus geometry hash).
Never let CFD preprocessing change the original floorplan/PlannerBuild geometry.

Required derived outputs:
- Closed/fluid-bounded room volume for selected connected region, with valid
  floor, internal ceiling, walls and any floor-opening side faces.
- Fully specified planar caps where selected domain stops at doors/windows.
- Named boundary patches (not a featureless unclassified STL), stable patch IDs,
  origin object references, coherent normals and dimensions/areas.
- Internal simplified obstruction geometry for furniture/people and equipment,
  clipped to the domain and tagged for boundary conditions and local refinement.
- Permanent passage openings must not be accidentally capped; resulting fluid
  surface should not contain interior artificial walls.
- Support non-rectangular L/T/U/recess footprints already available in planner.
- Support multiple levels, variable upper-floor footprints, floor-slab voids,
  flat/mono-pitch/gabled/stepped INTERIOR ceilings as implemented by the editor.
- If the active model lacks a reliable 3D solid/B-rep builder, first create a
  tested geometry-adapter abstraction and robust surface triangulation/export.
  Reuse existing libraries; choose Boolean/triangulation tools deliberately.
- Distinguish 'surface preview triangulation' from an actual CFD volume mesh.
- Keep world-to-solver transform explicit; choose deterministic SI units and
  normals, preserving the user's chosen display units in UI.
- Never infer walls/ceilings from visible GPU meshes alone if better semantic
  building geometry is available.

Preflight geometry QA:
- Missing faces, unbounded regions, degenerate zero-size walls/faces, nonmanifold
  edges, self-intersections, inverted normals, gaps beyond configured tolerance,
  overlaps, sliver surfaces, duplicate faces, invalid openings and isolated solids.
- Invalid vent placement (e.g. outside wall area, over a door/window, bridging
  incompatible patches, overlapping other vents or prohibited surfaces).
- Occupant/furniture proxies intersecting boundaries in invalid ways; report
  clear, actionable repairs.
- CFD air volume must be finite, positive and (except intentional inlet/outlet
  boundary patches) topologically enclosed for meshing.
- Explicit tolerances and tested failure modes; fail visibly, never silently
  create an open/leaky mesh.

Geometry preview:
- Selected volume translucent (differentiate wall, ceiling, floor, cap, vent).
- Optional section/cutaway, hide outer building floors, and selected-patch isolate.
- Named patches selectable in both a 3D viewer and a synchronized table.
- Show approximate dimensions/areas and accurate source object identity.
- If volumetric meshing is not integrated, say "CFD geometry preview", not
  "CFD mesh generated".

8. BOUNDARY CONDITION EDITOR (EVERY DOMAIN PATCH)
============================================================

Each selected fluid-domain boundary surface requires an identity and physically
meaningful boundary-condition family. Build an editable PATCH TABLE and a
synchronized 3D patch picker:

Patch categories: WALL, FLOOR, CEILING, DOOR, WINDOW, SUPPLY, EXTRACT,
PERMANENT-PASSAGE-INTERFACE (should generally disappear from external boundary
when volumes are merged), OBJECT_SURFACE, TEMPORARY_DOMAIN_CAP, OPEN_BOUNDARY,
SYMMETRY (expert), POROUS_INTERFACE (expert/future).

Boundary editor must support, as appropriate:
- Flow: no-slip, slip/symmetry where valid, fixed velocity or volumetric flow,
  mass-flow, pressure inlet/outlet, atmospheric/opening boundary; expert custom
  future mapping.
- Thermal: adiabatic, fixed temperature, specified heat flux W/m^2, heat
  transfer coefficient h + ambient reference T, outdoor design temperature;
  solar/radiation settings optional/deferred if solver lacks corresponding model.
- Scalar: CO2/species concentration and flux, including occupant source
  contributions where applicable.
- Vent turbulence: intensity/length scale or directly k/epsilon/omega if using
  a compatible turbulence model.
- Wall roughness, wall-function settings (expert), emissivity and material
  metadata where supported by the selected physics model.
- Door/window state: Open/Closed can pick a suggested BC preset, but NEVER
  changes volume-selection stop behaviour. Open door/window at domain edge
  may be modelled as pressure opening; closed one as solid with thermal BC.
- Reference/static pressure choice, gravity direction, consistent reference
  temperature and units; avoid over-constraining the flow problem.

Allow assigning a preset to a patch GROUP (all walls, all windows, etc.) with
per-patch overrides. Offer 'unassigned boundary' warnings and quick links to fix.
Don't expose mathematically impossible BC combinations for chosen physics. A
pressure outlet's specified static pressure and a flow-controlled outlet should
not both be active unless a documented supported specialised BC warrants it.

Save stable patch IDs, names, user assignments, surface area/normal, geometry
hash and source-object references, so later OpenFOAM mapping can be deterministic.

9. SIMULATION PARAMETERS / PHYSICS CONFIGURATION
============================================================

Allow users to define ALL important inputs needed to PREPARE an indoor CFD case,
with progressive disclosure rather than an unusable list of expert options.

Simulation case:
- Scenario name/description; operating scenario (occupied/unoccupied, design
  summer/winter, office ventilation, cooling, heating).
- Analysis mode: isothermal airflow, buoyant thermal airflow, or scalar/CO2
  transport; optionally transient. Clearly show which results are meaningful
  for each mode; treat unsupported solver combinations as 'planned'.
- Steady-state vs transient, solver family planned (do not hard-code a single
  executable), compressibility / Boussinesq assumptions where appropriate.
- Coordinate system, gravity vector, pressure reference, reference location.
- Site/design environmental conditions: indoor/outdoor T, reference pressure,
  air properties and humidity if used by actual model (otherwise metadata only).

Fluid properties (named Air preset, expert edits):
- Density, dynamic or kinematic viscosity, cp, conductivity, Prandtl and
  thermal expansion coefficient where relevant. Clearly document dependent
  fields and physical units; avoid inconsistent simultaneous independent
  values unless operating in an expert override mode.
- Operating/reference temperature. All values stored as solver-ready SI.

Flow/turbulence:
- Laminar or RANS; initial candidates k-epsilon and k-omega SST, with
  physically meaningful near-wall settings. More specialised modelling only
  where later backend supports it; don't offer LES as active without support.
- Initial velocity components, pressure, temperature, turbulent quantities,
  scalar/background CO2 concentrations. Define meaning of external reference
  CO2 and concentration units (ppm vs mass/mole fraction conversions).
- Inlet turbulence model/preset and characteristic length where relevant.

Thermal/transport:
- Enable gravity and buoyancy, wall/floor/ceiling heat transfer BCs, person
  and equipment heat sources, supply air T and thermal boundary materials.
- Optional scalar species and source strength (CO2 initially; possible passive
  tracer / age-of-air strategy later). Age of air requires proper transport
  formulation, not just a toggle that fabricates outputs.
- AC supply/return thermal balance and non-physical mass/heat-flow warnings.

Time/algorithm controls:
- Start/end time, timestep, automatic adjustable dt, target/max Courant
  number, write interval, statistics interval, initialisation strategy.
- Linear/numerical scheme preset, pressure-velocity coupling preset, non-
  orthogonal corrections, relaxation factors and tolerance controls (EXPERT
  only and future solver-mapped).
- Residual target per equation, physical monitor targets, max iterations/time,
  flow-balance tolerance and convergence rules that combine numerical residuals
  and engineering quantities (flow/temperature/pressure/CO2 monitors).
- Stationary solver and transient convergence/display expectations differ;
  document them in the UI.

Resource settings (future-run metadata):
- Requested CPU cores/parallel partitions, max wall time, memory limit,
  intended container/queue, output detail, output retention and storage limits.
- Resource fields should not suggest that OpenFOAM is currently connected.

Provide default validated example presets with explicit 'sample defaults, must be
validated for each project' wording. Allow custom configurations and 'Reset to
preset'. Units conversions must be tested; display SI/imperial as app supports.

10. MESH RECIPE, REFINEMENT AND QA
============================================================

Build a mesh-configuration screen rich enough that a later OpenFOAM adapter can
construct blockMesh/snappyHexMesh (or an alternative provider) WITHOUT asking
the user to re-enter key settings. Store mesh intent independently of mesher
command syntax and bind to a geometry hash.

Basic controls:
- Mesh preset: Draft / Standard / Fine / Custom. These are QUALITY INTENT
  presets and should not be represented as proven accurate for arbitrary rooms.
- Background mesh type/resolution: target global cell length, or cells per

- Target/max cell count and RAM/time cost estimates with clear uncertainty
  flags. No false actual cell counts until a real mesher runs.
- Separate tolerances for geometry cleaning, small features and snap distance.

Local refinements:
- Vent/inlet/outlet face and jet zone; stronger refinement near small vents.
- Doors/windows/terminated caps; recirculation-relevant opening edges.
- Walls/floor/ceiling, thermal boundaries and high gradients.
- People and furniture proxy surfaces; heat/CO2 source zones and wakes.
- Geometric subregions (box, sphere, zone by object) with custom target size
  or level and region labels; avoid redundant overlapping rules where possible.
- User-created refinement zones in 2D/3D with consistent transforms.

Near-wall treatment:
- Enable/disable boundary layers, target layer count, first-layer thickness,
  growth ratio, minimum thickness, smoothness/coverage and optional target y+.
- Interrogate selected turbulence/wall function and warn if y+ intentions and
  wall treatment are incompatible. No numerical claims of achieved y+ until
  a physical mesh and flow solution exist.

Mesher / quality advanced fields:
- Snapping, castellated mesh controls, edge/feature refinement, curvature
  sensitivity, refinement iteration/limit, balancing and cell-removal strategy.
- Max non-orthogonality, skewness, aspect ratio, min positive volume,
  concavity/face angles or comparable configurable acceptance thresholds.
- Candidate mesh generation/execution backend names stored as provider
  choices, but do not claim provider exists if it doesn't.
- Boundary patch mapping must survive meshing and remain traceable to vents,
  doors, windows, people/furniture and ceiling/floor parts.

What can be implemented NOW without OpenFOAM:
- All controls, validation, named refinement regions, 3D surface-region
  highlighting, approximate size/complexity estimates (label as estimates),
  geometry export manifest and persistent mesh recipe.

What cannot be honestly implemented without a real mesher:
- Actual 3D finite-volume cell tessellation, cell-quality histogram,
  checkMesh output or achieved mesh conformity. Keep those placeholders clearly
  disabled/not connected.

  dimension, missing mandatory boundary assignment, invalid vent host/area,
  impossible temperature/pressure units, mutually exclusive BC conflict,
  invalid/refinement size, non-positive timestep or impossible solver settings.

Warnings, not automatic hard failures where context matters:
- No supply, no outlet, mass imbalance with no pressure opening, inadequate
  physical constraint, vent too close to wall/furniture, furniture too detailed
  relative to requested cell size, missing heat/CO2 data in thermal/scalar mode,
  target resources likely too low, unsupported ceiling shape for mesh.

Use a stable JSON representation of the complete CFD scenario, plus a
 geometry/patch manifest, recipe files and an optional surface-geometry export
(if implementation is ready and valid). Clearly state exporter capabilities:
writing a JSON manifest is NOT equivalent to creating a runnable OpenFOAM case.

Allow explicit actions:
- Save scenario to project / load / duplicate / restore revision if project
  already has versioning / export JSON / import validated JSON.
- Download preflight report and human-readable settings summary.
- Export surface geometry + BC patch manifest only if geometry builder can
  produce reliable faces/normals; otherwise report the limitation.
- Future (disabled until adapter): Generate mesh, Run CFD, Stop/Cancel, Retry,
  view console logs, inspect convergence graphs, download results.

All scenario snapshots include modelRevision/geometryHash, scenarioRevision,
units, application schemaVersion, timestamp and backendProvider identity/status.
Mark an existing run/mesh 'STALE' if geometry, BC, physics or mesh inputs change.
Never present old results as current for an edited model.

17. SPECIFIC RISK REGISTER AND CLARIFICATIONS
============================================================

1. DOOR/WINDOW HARD STOP IS INTENTIONAL, NOT A BUG. In reality air can cross an
   open door, but this MVP models it as a CFD DOMAIN BOUNDARY, not a portal
   connecting rooms. Prescribe the appropriate flow/pressure BC at the plane.

2. PERMANENT OPENINGS ARE DIFFERENT from open doors. If the present floorplan
   data cannot distinguish an archway from an open door, introduce an explicit
   passage/opening type rather than guessing from a state flag.

3. GEOMETRIC 'WATERTIGHT' does NOT mean all patches are no-slip walls. An open
   boundary is geometrically capped and physically assigned an opening BC.

4. MULTI-ROOM CONNECTIONS MUST BE PHYSICALLY CORRECT. No blind graph union of
   rooms with merely adjacent walls. If robust connectivity detection is hard,
   use explicit portal semantics and validation. Avoid inconsistent results.

5. ROOF VS CEILING: Only the INTERNAL ceiling should bound interior CFD air.
   An external pitched roof above a suspended ceiling is outside the CFD room.

6. PRECISION: Small vents and furniture may need much smaller cells than global
   room dimensions; keep cell count estimates labelled, constrain tiny shapes.

7. PEOPLE: A human proxy blocks flow AND can emit sensible heat and CO2. Don't
   assume one scalar per person is accurate for every activity/temperature.

8. PHYSICS COMPLEXITY: UI can store advanced options, but actual compatible
   OpenFOAM mapping and validated defaults must be demonstrated later. Never
   mark an unimplemented model 'supported' just because it appears in a form.

9. CFD RESULTS: Setting fields and settings does not equal actually solving.
   OpenFOAM and adjoint connectivity is FUTURE WORK. No placeholder output that
   masquerades as computed results.

10. OPTIMISATION: User-placed vent positions and constrained movable footprints
    must be represented now, but adjoint field projection / porous mask algorithm
    remains R&D and is NOT to be implemented until after CFD validation.

11. PRODUCT SCOPE: Avoid full BIM, whole-building airflow through arbitrary
    doors/windows, detailed radiation, heat conduction through whole walls,
    HVAC control systems or equipment catalogues in this first implementation.
